Windows Patch Automation Framework

Patch Windows VMs on VMware vCenter without RDP or WinRM. The runner connects to vCenter only; VMware Guest Operations runs update scripts inside each guest using the native Windows Update COM API.

Guest Operations only PowerCLI + PowerShell 7 JSONL audit logs Sep 15, 2026 · v1.2

End-to-end flow

From operator action to compliance report — every VM is an isolated worker with its own vCenter session.

flowchart TD
    A[Load config and credentials] --> B[Validate environment]
    B --> C{VM and guest creds OK?}
    C -->|No| D[Stop and fix inventory or creds]
    C -->|Yes| E[Connect vCenter]
    E --> F[Find VM by name or IP]
    F --> G[Wait for VMware Tools]
    G --> H[Copy scripts into guest]
    H --> I[Repair WU COM if needed]
    I --> J[Patch cycle: scan install]
    J --> K{Updates remain?}
    K -->|Yes| L[Reboot if required]
    L --> M[Warm up and verify convergence]
    M --> J
    K -->|No| N[Mark Compliant]
    N --> O[Export reports and JSONL logs]

Happy path in three steps

  1. Validate — vCenter login works; VM exists; guest account works via a test hostname command.
  2. Patch loop — Scan, download, and install all pending updates; reboot when required; repeat until zero pending.
  3. Report — Compliance JSON/CSV/HTML plus per-VM logs under output/<run-id>/.

Quick start

Prerequisites

  • VMware Tools running on target VMs (guestToolsRunning)
  • Two credential pairs: vCenter SSO + Windows local admin inside each VM
  • PowerCLI 13.3 and PowerShell 7.2+ on the runner
  • Guest can reach WSUS or Microsoft Update

Run locally (fleet)

cd /home/tpx-admin/.cursor-server/Windows-Patch-Automation-Framework
unset VCENTER_USERNAME VCENTER_PASSWORD WINDOWS_GUEST_USERNAME WINDOWS_GUEST_PASSWORD
source ~/.windows_patch_creds

# Validate only (enabled rows in config/vms.csv)
pwsh -File ./scripts/Validate-PatchEnvironment.ps1

# Patch all enabled VMs in config/vms.csv (parallel, throttled)
./scripts/execute_patch.sh

Inventory row

Set Enabled=true in config/vms.csv only for approved VMs. Use exact vCenter VM name or provide IP for fallback lookup.

Execution commands

Run from the Linux runner (blr-kiruthika). Credentials are loaded with source — never execute the cred file directly.

1. Credential file

Create one file per guest password group (same password can share one file):

vi ~/.windows_patch_creds
chmod 600 ~/.windows_patch_creds
export VCENTER_USERNAME="ks4@vsphere.local"
export VCENTER_PASSWORD="your-vcenter-password"
export WINDOWS_GUEST_USERNAME="admin"
export WINDOWS_GUEST_PASSWORD="your-guest-password"

Example: admin for NEPTUNE/damo VMs; Administrator for DHA — use separate files if passwords differ:

~/.windows_patch_creds          # damo / admin VMs
~/.windows_patch_creds_dha       # BLR-DHA-TESTING02 / Administrator

cd /home/tpx-admin/.cursor-server/Windows-Patch-Automation-Framework

Fleet run (all VMs at once)

Use this when you want to patch every server listed in the main inventory (config/vms.csv) — the same list used for scheduled GitHub Actions.

Before you start

  • Every VM you enable must use the same guest account for that run (admin or Administrator, one password).
  • If passwords differ, split into batches (separate CSV + cred file per batch) — do not mix in one run.
  • Take vCenter snapshots on production VMs before a fleet patch.
  • Confirm VMware Tools are running on all targets.

Edit config/vms.csv (or export from Excel and save as CSV with the same columns). Set Enabled=true only for VMs approved this window.

GitHub pipeline (Actions)

Yes — you can trigger patching from the GitHub repo. Workflow file: .github/workflows/windows-patch.yml.

What runs

  1. Validate — Pester tests on GitHub-hosted Ubuntu (no vCenter needed).
  2. Patch — Full fleet patch on a self-hosted Windows runner with labels self-hosted, windows, vcenter.
  3. Artifacts — Uploads output/ (reports + JSONL logs) for 30 days.

Prerequisites (one-time)

  • Self-hosted Windows runner registered to the repo with labels above and network access to vCenter (HTTPS 443).
  • GitHub environment windows-patching with secrets: VCENTER_USERNAME, VCENTER_PASSWORD, WINDOWS_GUEST_USERNAME, WINDOWS_GUEST_PASSWORD.
  • Target VMs listed in config/vms.csv with Enabled=true.
  • One guest password per workflow run — batch only VMs that share the same guest credentials.

Manual trigger from GitHub UI

  1. Open Actions → Windows Patch Automation.
  2. Click Run workflow (dropdown on the right).
  3. Select branch main, then Run workflow.
  4. Wait for job Validate framework, then Patch Windows fleet.
  5. Download artifact windows-patch-results-<run-id> when complete.

Trigger from CLI (gh)

gh workflow run windows-patch.yml --repo Kiruthika-syk/Windows-Patch-Automation-Framework

# Watch run status
gh run list --workflow=windows-patch.yml --repo Kiruthika-syk/Windows-Patch-Automation-Framework
gh run watch --repo Kiruthika-syk/Windows-Patch-Automation-Framework

Scheduled runs

Cron is configured for Sunday 02:00 UTC (0 2 * * 0). Edit the workflow file to change the schedule.

GitHub vs Linux runner

GitHub Actions patches all enabled VMs in config/vms.csv using repo secrets.

Linux runner (blr-kiruthika) is better for single-VM runs via output/*-only.csv and per-server cred files — what you use for damo/DHA testing today.

Two separate credential pairs — never mix them up.

Network path

Runner ──HTTPS 443──► vCenter (e.g. blr-vsphere-01.strykercorp.com) │ └── VMware Tools ──► Windows guest Invoke-VMScript · Copy-VMGuestFile

  • Guest downloads updates via its normal Windows Update / WSUS path.

Update checking process

Runs inside the guest via Microsoft.Update.Session COM API.

  1. Warm-up — After recent reboot, start WU services and wait 45–90 seconds.
  2. Primary scan — IsInstalled=0 and IsHidden=0
  3. Definition scan — Same criteria plus CategoryIDs contains '798' (Defender / definition updates).
  4. Merge — Combine results so security intelligence updates are not missed.
  5. Evaluate — Zero updates + no registry reboot pending → NoUpdates (done).

Reboot detection uses registry keys (CBS, WU RebootRequired), not only the COM RebootRequired flag — this prevents false reboot loops after updates are installed.

Update installation process

  1. Accept EULAs for each applicable update.
  2. Download all updates in one batch (CreateUpdateDownloader).
  3. Install all downloaded updates in one batch (CreateUpdateInstaller).
  4. Record per-update title, KB, result code, HRESULT, reboot flag.
  5. Write cycle-N-result.json atomically; runner polls for this file.

If COM fails with 0x800703FA shortly after reboot, the guest waits and retries before renaming the SoftwareDistribution cache.

Orchestrator patch loop

For each enabled row in config/vms.csv, up to throttleLimit VMs run in parallel.

PhaseWhat happens
ConnectConnect-PatchVCenter with exponential retry
Resolve VMBy name; fallback match by IP from inventory
Tools readyPoll until guestToolsRunning and guest state = running
StageCopy patch + repair scripts to guest working directory
RepairQuick COM test; basic repair; DISM/SFC only if still broken
Cycle 1..NStart async guest job → poll → copy artifacts
RebootRestart-Computer → wait Tools → 90s service warm-up
Convergence0 pending + no registry reboot → Compliant

Final status values

StatusMeaning
CompliantNo pending updates; convergence verified
MaxCyclesExceededSafety cap hit (updates may still have installed)
FailedHard error: COM, timeout, auth, etc.

Security

  • Credentials live in environment variables or GitHub secrets — never in CSV, logs, or reports.
  • Guest scripts run as local admin only through VMware Guest Operations (audited in vCenter).
  • No inbound management ports required on VMs beyond VMware Tools and Windows Update egress.
